# ИДЗ №2 по АКОС. Вариант 32 «Кухня ресторана»

Исполнитель: **ФИО — _заполнить_**, группа **_заполнить_**.

## 1. Условие

В ресторан приходят посетители и заказывают одно или несколько блюд. Официант принимает заказ и передаёт на кухню. Блюдо — цепочка операций, каждой нужны повар и оборудование одного типа (плита, печь, гриль, стол). Повара берут готовые к выполнению операции из очереди; одна единица оборудования обслуживает одну операцию. Готовые блюда собираются по номеру заказа, официант отдаёт заказ только своему посетителю и только когда готовы все блюда. Очереди кухни и зона готовых блюд ограничены. Невыполнимые заказы отменяются. Программа завершается после обслуживания всех принятых посетителей, отмены невыполнимых заказов или по сигналу (в бесконечном режиме).

Реализовано на C11 + pthread, Linux. Две программы: `kitchen_sem` (мьютексы + семафоры) и `kitchen_cv` (мьютексы + условные переменные).

## 2. Потоки

| Сущность | Потоков | Что делает |
|---|---|---|
| main | 1 | читает конфиг, создаёт потоки, по одному впускает посетителей с интервалом, ждёт, печатает статистику |
| Посетитель | N | садится в зал, ждёт заказ на личном семафоре, ест, уходит; нет места — уходит сразу |
| Официант | W | берёт из общей очереди посетителя (принять заказ) или готовый заказ (выдать) |
| Координатор кухни | 1 | разбивает заказ на блюда и операции, в очередь ставит только операции без незавершённых предшественников, собирает блюда, отменяет невыполнимые заказы |
| Повар | C | берёт операцию, занимает единицу оборудования, готовит (sleep), освобождает, отчитывается |
| Сигналы | 1 | `sigwait` на SIGINT/SIGTERM; в остальных потоках сигналы заблокированы |

Путь заказа: зал → очередь официантов → очередь заказов → координатор → очередь операций → повар → очередь отчётов → координатор → зона готовых блюд → официант → семафор посетителя.

Модули: `bqueue` (очередь), `sync.h` + `sync_sem.c` / `sync_cv.c`, `log` (вывод), `config`, `equip` (оборудование), `kitchen` (потоки-участники), `main`.

## 3. Синхронизация

* **Очереди** — один модуль `bqueue`: кольцевой буфер под мьютексом, семафоры «свободно»/«занято». Активного ожидания нет, `sleep` только имитирует время. Очередь операций отдаёт элемент с наименьшим ключом (равные — FIFO): `fifo` — все равны, `vip` — VIP-заказы раньше, `short` — меньший заказ раньше.
* **Оборудование** — на каждый тип счётный семафор (сколько единиц свободно) и массив занятости под мьютексом (чтобы напечатать номер единицы).
* **Посетитель** — личный семафор «заказ принесли».
* **Вывод** — одна функция `log_event` под мьютексом, `write()` в fd 1 и в файл лога.
* **Проверки** — `CHECK(cond, "текст")` перед действиями по счётчикам под мьютексом; нарушение пишет `НАРУШЕНИЕ` в лог и даёт код 2. В конце проверяется: принятые = обслуженные + отменённые, очереди пусты, оборудование свободно.
* **sem и cv.** `sync.h` даёт «счётный семафор» `ksem_*` и `sync_sleep`. В `sync_sem.c` это `sem_t`, в `sync_cv.c` — счётчик + мьютекс + `pthread_cond_t` с ожиданием в `while`. Остальной код один и тот же.

### Почему нет дедлока

1. Координатор берёт заказ в работу, только заняв слот зоны готовых блюд (`ready_slots`); слот освобождает официант при выдаче. Поэтому блюд «в полёте» не больше, чем слотов × размер заказа, а готовые блюда всегда есть куда положить: без этого заказы могли бы занять все очереди и повара ждали бы места под готовое блюдо, которое освободит только уже невозможный заказ.
2. Координатор — единственный, кто может заблокироваться на очереди операций, и он ждёт только поваров. Повара никогда не блокируются на отчётах (очередь отчётов вмещает все блюда заказов, занявших слот), а оборудование всегда рано или поздно освобождается, потому что повар держит ровно одну единицу.
3. Очереди официантов и заказов имеют ёмкость, равную числу мест в зале: у каждого сидящего посетителя в них не более одной записи, поэтому `put` туда не блокируется.
4. Повар держит не более одной единицы оборудования, ждать ему больше нечего — циклического ожидания нет.
5. Координатор ждёт на одном семафоре-«звонке» (его поднимают заказ, отчёт, освобождение слота) и после пробуждения разбирает всё без блокировки, поэтому не может «проспать» событие из другой очереди.

## 4. Интерфейс и запуск

```
./kitchen_sem [-c config] [-s seed] [-l log] [-t ms] [-q]
```

* `-c` — конфиг (формат — в `tests/basic.cfg`). Без `-c` основные параметры спрашиваются с клавиатуры (Enter — по умолчанию).
* `-s` — seed (печатается в начале); у каждого потока свой seed для `rand_r`.
* `-l` — файл лога (`O_CREAT|O_TRUNC`, 0644, по умолчанию `kitchen.log`); `-t` — мс в единице времени модели; `-q` — в stdout только итог.
* Ключи конфига: `customers waiters cooks arrival eat equipment dish order hall_queue op_queue ready_slots priority vip max_dishes`. Ошибка конфига — сообщение с номером строки и код 1.

Завершение: все посетители обслужены или отменены → `main` ждёт посетителей, кладёт в очереди `NULL`, делает `join` всем потокам. `customers 0` — бесконечный режим до сигнала. Первый Ctrl+C: новых не пускаем, доделываем принятые; второй: немедленный выход (ждущие потоки будятся, оборудование освобождается). Лог и статистика сохраняются в обоих случаях. Коды возврата: 0 — норма, 1 — ошибка конфига/аргументов/системного вызова, 2 — нарушен инвариант.

Сборка: `make`, `make test`, `make tsan` (`-fsanitize=thread`).

## 5. Результаты

`make test` (обе программы, 15 проверок каждая): базовый, параллельный, один гриль на всех, все очереди = 1, невыполнимый заказ (oven 0) с уведомлением посетителя, приоритеты vip и short, битый конфиг с номером строки, отсутствующий файл, неверный аргумент, повтор по seed, бесконечный режим с одним SIGINT / двумя SIGINT / SIGTERM. Все проходят, `НАРУШЕНИЕ` нет. `make tsan` — те же тесты под ThreadSanitizer, предупреждений нет.

Пример итога (`-c tests/basic.cfg -s 42`):

```
Заказы: принято 6, обслужено 6, отменено 0, прервано 0
Ожидание заказа (от прихода до выдачи): среднее 22.73, максимальное 40.60 ед.
Загрузка оборудования: печь 84.5%, гриль 56.4%, стол 21.4%, плита 0.0% (в меню basic.cfg нет блюд на плите)
```

В базовом конфиге зал на 4 места и узкое место — одна печь, поэтому часть посетителей уходит без места (6 из 12). Это штатный сценарий, а не ошибка.

## 6. Сравнение sem и cv

Поведение и результаты одинаковы (при одном seed — те же посетители и заказы; тайминги отличаются на доли единицы). Семафоры короче: ожидание и счётчик в одном объекте. Вариант на условных переменных требует вручную держать счётчик под мьютексом и цикл `while` против ложных пробуждений, зато даёт тайм-аут по монотонным часам и простое пробуждение всех ждущих (`broadcast`) при аварийной остановке. Для остановки в варианте sem приходится считать ждущих и делать столько `sem_post`.
